    评分标准¶

    共50分，其中实验功能40分，代码规范5分，实验报告5分。

    实验的时间安排：

    1. 2026年8月20日（周四）开始讲解大作业。
    2. 爬虫和 Web 系统设计的功能实现，在 2026年9月1日（周二）由助教线下验收。（验收形式后续通知）
    3. 数据分析结果（可以写数据分析报告或者写在实验报告内）、实验报告以及所有源代码，在 2026年9月1日（周二）23:59 前提交至网络学堂。
    4. 作业原则上不接受补交。需要有足够的原因（如医学证明）才能接受补交，且每人仅有一次补交机会。
    5. 本次大作业要求手写。在验收环节助教会考察同学们对代码的熟悉和理解，滥用 AI 工具者无法拿到对应部分的分数。

    关于 AI 使用的说明

    本次作业难度和工作量均尚可，要求手写是希望同学们能熟悉 Python 语言和一些基础知识。在学习之初滥用 AI 工具会无益于自身成长，也不利于同学们准备第四周的上机考试，希望同学们能理解并遵守。此规则解释权归教学团队所有。

    实验功能¶

    • 爬虫（10分）
      • 爬虫代码正确可运行
        • 能够正常发送请求、解析页面或接口返回的数据
        • 能够提取并保存实验要求的歌曲和歌手信息
      • 爬取数据数量满足要求
        • 歌曲不少于 2000 首，歌手不少于 100 位
        • 每位歌手至少对应一首歌曲
        • 用于网站展示的歌曲和歌手信息基本完整
    • Web系统设计（20分）
      • 歌曲列表页
        • 正确展示系统中的歌曲
        • 使用分页方式展示，并提供要求的翻页和页码跳转功能
        • 点击歌曲可以进入对应的歌曲详情页
      • 歌手列表页
        • 正确展示系统中的歌手
        • 使用分页方式展示，并提供要求的翻页和页码跳转功能
        • 点击歌手可以进入对应的歌手详情页
      • 歌曲详情页
        • 展示歌曲名、歌手名、歌曲图片、歌词和原始网站 URL
        • 点击歌手名可以进入对应歌手详情页，原始网站 URL 可以正确跳转
        • 支持评论的提交、持久保存、倒序展示和删除
      • 歌手详情页
        • 展示歌手名、歌手图片、简介和原始网站 URL
        • 展示该歌手在系统中的全部歌曲
        • 歌曲条目包含名称和图片，并可进入对应歌曲详情页
      • 搜索和搜索结果页
        • 可以选择搜索歌曲或歌手，并按照要求的字段进行子串搜索
        • 搜索结果正确，并使用分页方式展示
        • 显示搜索结果数量和后端搜索耗时
        • 点击搜索结果可以进入对应详情页
      • 搜索性能和网页整体效果（含美观度）
        • 在要求的数据量下，搜索时间控制在 1 秒以内
        • 网站各页面之间可以通过页面控件正常跳转
        • 页面布局清晰，文字、图片和控件能够正常展示
        • 不同页面的样式基本统一，主要功能便于使用
    • 数据分析（10分）
      • 三个结论在所爬数据下正确
        • 每个结论均有相应的分析代码
        • 通过文字说明分析方法和过程
        • 使用合适的图表或数据支持结论
      • 数据分析结论的质量
        • 结论有意义，论证合理
        • 可视化清晰，能够支持结论

    代码规范（5分）¶

    本项主要考察 Git 使用、代码格式与命名、注释与文档以及模块组织。本节列举了作业中应遵循的代码规范，目的是帮助大家养成良好的开发习惯。

    Git¶

    Git入门

    如果你还没有使用过 Git，可以参阅 本地 Git 安装与配置指南 及其包含的链接内容，了解 Git 的基本使用方法。

    • 使用 Git 进行版本控制。
    • 每个提交都应具有具体意义，例如实现新功能、修复问题、编写新函数等；
    • 对于较复杂的项目，应边开发边提交，避免将大量更改一次性提交；
    • 配置合理的 .gitignore 文件，避免提交不必要的文件（如二进制文件、IDE 配置文件等）；
    • 用简明的语言描述本次提交的内容；
    • 建议用英文书写，中文亦可；
    • 保持信息的适度详实，不要过于简略或冗长；
    • 推荐遵循 Conventional Commits 的格式；
    • 内容应避免个人情绪；
    • Git 用户名和邮箱应配置为真实姓名和邮箱；
    • 可适当添加 Emoji，gitmoji 提供了推荐列表方便参考。

    代码风格¶

    保持代码简洁、清晰：

    • 保持整齐的缩进，推荐使用4 个空格作为一级缩进（遵循 PEP8）；
    • 每行字符不应过多，建议不超过 79/88/120 个字符（PEP8 标准为79，black 默认 88 个字符，PyCharm 默认 120个字符）；
    • 减少硬编码和 magic number：例如，若多处出现 3.14，应定义 PI = 3.14 在顶部，后续均使用 PI。

    在代码编写适当注释和文档：

    • 复杂代码块前应对其功能、逻辑简要说明；
    • 对过于简单的代码可不写注释，避免冗余；
    • 所有函数/类建议编写文档字符串（docstring），描述其功能、参数类型和返回值，推荐加以类型标注；
    • 推荐使用英文，中文亦可（但是注意要用 UTF-8 编码）；
    • 参考阅读：PEP257 Python docstring 规范。

    代码应合理使用空格和空行：

    • 功能分段之间增加空行，提升可读性；
    • 操作符前后、逗号后等规范加空格（如 result = a + b、print(a, b)）；
    • 保持前后风格一致，如统一的缩进风格和空行数量。

    变量、函数、类的命名应符合下列标准：

    • 变量、函数使用小写字母和下划线（snake_case），类名使用首字母大写的单词（CamelCase），常量用全大写字母和下划线；
    • 尽量使用有意义的英文单词命名，避免中文、拼音及无意义短名（如 a, b, c 等）；
    • 尽量用英文单词，而不是中文拼音首字母；
    • 命名应与实际用途及上下文相关联；
    • 参考阅读：PEP8 命名推荐。

    对于较复杂的项目，不应将所有代码写在同一文件中：

    • 应按功能将代码拆分到多个 .py 模块，并合理组织到包结构中；
    • 参考阅读： Python 官方模块和包说明。

    为实现上述规范，可考虑利用以下自动化工具：

    • 大多数现代编辑器（如 VSCode、PyCharm 等）都集成了格式化与静态检查工具
    • 可以使用 black 进行代码自动格式化：
      • 命令行用法：black .
      • 编辑器用法：在 VSCode 或 PyCharm 设置中启用 black，保存文件时会自动格式化。
    • 可以使用 pylint 进行代码静态检查：
      • 命令行用法：pylint your_code.py
      • 编辑器用法：在编辑器安装相关插件或启用检查功能，保存或编辑时自动显示代码警告和建议。
